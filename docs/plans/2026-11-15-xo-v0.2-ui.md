# XO v0.2 — new UI, Projects, question answering: implementation plan

Date: 2026-11-15
Status: ready to implement (interview done by the coordinator on 2026-11-15; unsettled points are in section 12)
Builds on: `docs/plans/2026-11-15-xo-v0.1.md` (section 6 "Amendments" there is the current truth for everything this plan does not change).

## 1. Objective

Replace the cramped TUI client with a calm, readable UI modelled on the Claude desktop app: a light/dark sidebar, one ongoing conversation stream, and the opened document in a right-hand panel. Add **Projects** as a document type that actions and notes can belong to. As the last step, let XO **answer questions** from the user's own data, sending only relevant excerpts to the LLM.

Why (user): the TUI is hard to read, navigation is unclear, vim keys feel awkward, and the chat does not feel like a conversation.

## 2. Scope

### In scope

- New client (Preact + `@preact/signals` stay): sidebar, conversation stream + composer, document panel (closable, expandable), phone layout, system light/dark theme, proportional system font.
- Ordinary shortcuts, **no modes**. Voice stays first-class (push-to-talk, mic button in the composer, voice commands).
- Projects: table, CRUD, linked people, `actions.project_id`, `notes.project_id`, classifier and capture pipeline support, `#project` prefix, search, soft delete + 30-day purge, Markdown export.
- Sidebar "Pinned" (people, projects) and "Recents" (last 15 opened people, projects, 1-1s, notes), stored on the server.
- Actions page grouped by project and filterable by person; a 1-1 shows the person's open actions across projects.
- Last: question answering in the stream (retrieval on the server, size cap, answer with clickable sources).
- Deploy to the `~/.xo/app` worktree after a clean review (coordinator).

### Out of scope

- Separate chats/threads, Markdown rendering (bodies stay plain text, `white-space: pre-wrap` — still the XSS-avoidance choice), resizable split, drag and drop, due dates, calendar, reminders.
- Project templates, sub-projects, ordering of actions inside a project.
- Streaming answers, follow-up questions with conversation memory, web search, embeddings/vector index.
- Offline mode and a service worker. (A web app manifest is added so XO can be installed as a window; nothing is cached offline.)
- Changes to auth, sessions, CSRF, the guard or the OpenRouter client's transport rules.

## 3. Approach

**New client, same server.** The client is rebuilt around a three-column shell; the server keeps its structure and gains projects, pins/recents and (last) Q&A.

|---|---|

| `lib/store.ts`: session, `epoch()`, `appPhase`, lock on 401, drafts, chat draft + voice-source tracking, flash, logout, auth channel | remove `mode`; add `projects`, `nav`, UI prefs; focus requests move to `lib/focus.ts` |
| `lib/draft-saver.ts`, `components/TextEdit.tsx` | restyle only; same draft/epoch rules |
| `views/chat-logic.ts`: send queue, landed feed, capture list merge, history recall, question helpers | moves to `stream/stream-logic.ts`; letter-hotkey helpers go |

| `lib/keys.ts` token parsing, layers, palette registry, fuzzy filter | modes and key sequences removed; region-based scopes added |
| Whole server | additive changes only |

Removed: `styles/tui.css`, `components/Pane.tsx`, `components/StatusBar.tsx`, all old `views/*.tsx` except `Login.tsx`, `views/nav-logic.ts`, `e2e/smoke.spec.ts`, NORMAL/INSERT/COMMAND modes, `j/k`, `g`-prefixes, single-letter commands.

Alternatives rejected: restyling the TUI views in place (the mode model and pane layout are what the user dislikes; every view would be rewritten anyway), and a second client package next to the old one (two clients to keep secure).

**One interaction pattern everywhere.** In the stream and in every document list: Up/Down pick a row, Left/Right pick one of that row's action chips, Enter runs it. Chips are also real buttons (click, touch, Tab). No letter commands exist, so stray typing can never trigger an action; a printable key pressed outside a text field goes to the composer.

**Contracts first, as in v0.1.** Step S1 lands the schema, shared types and API shapes; step C1 lands the client shell, key engine, router, store and component kit with stubs at the final paths. Later steps only fill in files they own.

**Every client step ships a real-browser check** as its own Playwright spec file. To make that safe for programmers working in parallel in one checkout, C1 changes the e2e setup to build the client into a per-run temp directory (section 4.9).

## 4. Architecture and contracts

Binding for all steps. If a step needs a contract change, it reports to the coordinator instead of editing a file it does not own. All CLAUDE.md conventions apply (`.ts` import extensions, erasable syntax only, strict ajv, routes inside the guarded `/api` scope with relative paths, every route with params/query/body schemas, parameterized SQL, shared error shape, no content in logs, CSP `style-src 'self'`).

### 4.1 Layout and behaviour

Desktop (viewport ≥ 900 px), CSS grid `sidebar | chat | panel`:

- **Sidebar** (260 px, collapsible): `+ New`, `Search`, `Actions`, `Notes`, `People`, `Projects`; then collapsible **Pinned** and **Recents**; footer with Shortcuts and Log out.
- **Chat column**: the stream (`role="log"`) and the composer pinned at the bottom. With no panel open it is centred (max-width about 760 px).
- **Panel**: the document named by the route. Header: back, title, expand/collapse, close. Open: chat and panel share the width (each min 380 px). Expanded: the panel takes the whole main area and the chat column is not rendered. Esc closes the panel.

Phone and narrow windows (< 900 px), "single-panel mode": the sidebar is a slide-in drawer (menu button, closes on navigation and Esc); either the chat or the document is shown; the document has a back button that returns to the chat; the composer sits at the bottom of the chat with a large mic button. Use `100dvh`, `env(safe-area-inset-*)`, `viewport-fit=cover`, form fonts ≥ 16 px (no iOS zoom), and `min-height: 0` down the whole flex chain of the stream.

Routes (hash; no query strings, search text never enters the URL):

| Hash | Route name | Panel |
|---|---|---|
| `#/` (also legacy `#/chat`, `#/search`) | `home` | none |
| `#/actions`, `#/notes`, `#/people`, `#/projects` | `actions`, `notes`, `people`, `projects` | list document |
| `#/notes/:id`, `#/people/:id`, `#/projects/:id`, `#/meetings/:id` | `note`, `person`, `project`, `meeting` | detail document |

Closing the panel (Esc ladder, Close button): if the history entry just left is `/` (stored in the pushed history state), `history.back()`; otherwise `navigate('/', { replace: true })`, so browser Back never reopens a closed document (amended after the C1 review). The panel's back button is `back()` (history when this app pushed an entry, else the parent list). Search is an overlay, not a route.

### 4.2 Keyboard (no modes)

The user is on macOS and probably a Swedish keyboard, so shortcuts use letters only (`/`, `?`, `:` need Shift there) and never Option+letter (it types a character and changes `e.key`).

| Key | Does | Conflict check |
|---|---|---|
| Cmd-K (Ctrl-K) | Open "Search and commands" (palette: commands, people and projects by name, server search) | Free in Chrome and Safari tabs; widely used by web apps |
| Cmd-J (Ctrl-J) | Focus the composer ("new capture"); in single-panel mode goes to the chat first | Chrome/Safari "Jump to selection": a menu shortcut the page can pre-empt |
| Cmd-N | Same as Cmd-J, **best effort** | **Not deliverable in a normal Chrome or Safari tab** (the browser opens a window before the page sees the key). Bound anyway so it works wherever the browser delivers it. Whether an installed app window delivers it is unverified: manual check (section 7) |
| Cmd-B (Ctrl-B) | Toggle the sidebar / drawer | Free (bookmark shortcuts use Shift or Option) |
| Esc | Close the top overlay; else cancel a recording; else leave a panel text field (it saves); else close the panel and focus the composer; else focus the composer | — |
| Up / Down | Move in the focused list or the stream | Never bound while a text field has focus |
| Left / Right | Pick an action chip of the highlighted row | same |
| Enter | Run the highlighted chip (default: the row's first, non-destructive action) | Focused buttons, links and checkboxes keep native Enter/Space |
| Tab / Shift-Tab | Native focus order between lists, fields and buttons | — |
| Option-Space (hold) | Push-to-talk anywhere | Kept from v0.1. Launchers (Raycast, ChatGPT) may claim it system-wide; then use the mic button. The key is one constant in `lib/keymap.ts` |
| Space (hold) | Push-to-talk when focus is not in a text field or on a button | Kept from v0.1 |
| Composer: Enter / Shift-Enter | Send / newline | — |
| Composer: Up in an empty composer | Move into the stream at the newest item | Native caret movement otherwise |
| Composer: Option-Up / Option-Down | Recall earlier texts (kept from v0.1) | Overrides paragraph-jump inside the composer only |
| Any printable key outside a text field | Focuses the composer and types there | — |

Not bound, on purpose: Cmd-T/W/Q/H/M/L/R, Cmd-digits, Cmd-arrows, Ctrl-arrows (Mission Control), Ctrl-Space, Ctrl-Tab, Cmd-F (browser find stays), Cmd-Z (text undo stays; "Undo" is a chip and a palette command).

The "new capture" answer to the Cmd-N problem is therefore: Cmd-J always works, typing anywhere lands in the composer, `+ New` in the sidebar, and Cmd-N as a bonus where delivered. A web app manifest lets the user install XO as its own window (Chrome "Install", Safari "Add to Dock").

Playwright synthesizes keys inside the page, so it cannot prove a shortcut is free in a real browser. The conflict column is checked by hand on real Chrome and Safari (section 7).

### 4.3 Database (`src/server/db/migrations/005-projects.sql`, step S1)

No table rebuilds: new tables plus `ALTER TABLE … ADD COLUMN` (nullable, default NULL, which SQLite allows with `REFERENCES`).

```sql
CREATE TABLE projects (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL,
  aliases TEXT NOT NULL DEFAULT '[]',              -- JSON string[]
  status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','on_hold','done')),
  description_md TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL, deleted_at TEXT
);
CREATE TABLE project_people (
  project_id INTEGER NOT NULL REFERENCES projects(id),
  person_id INTEGER NOT NULL REFERENCES people(id),
  created_at TEXT NOT NULL,
  PRIMARY KEY (project_id, person_id)
);
ALTER TABLE actions ADD COLUMN project_id INTEGER REFERENCES projects(id);
ALTER TABLE notes ADD COLUMN project_id INTEGER REFERENCES projects(id);
CREATE INDEX actions_project ON actions(project_id);
CREATE INDEX notes_project ON notes(project_id);
CREATE TABLE pins (
  kind TEXT NOT NULL CHECK (kind IN ('person','project')),
  item_id INTEGER NOT NULL, created_at TEXT NOT NULL,
  PRIMARY KEY (kind, item_id)
);
CREATE TABLE recents (
  kind TEXT NOT NULL CHECK (kind IN ('person','project','meeting','note')),
  item_id INTEGER NOT NULL, opened_at TEXT NOT NULL,
  PRIMARY KEY (kind, item_id)
);
```

`pins` and `recents` hold ids only, never titles. Agenda items have no project.

### 4.6 Capture pipeline with projects (step S3)

Prefix syntax (decision): **`#name`** or **`#"Full title"`** anywhere in the text marks an explicit project, parallel to `@person`. The `#` must not follow a letter or digit, and the first character after it must be a letter (so `#1` and `issue #42` are plain text; `# heading` too). In the cleaned text `#name` becomes the plain name. Projects are created from the Projects page, the palette ("New project"), or the "Create project" answer below; there is no `/project` command.

```ts
// src/shared/capture-syntax.ts
export interface ParsedCapture { forcedKind: ItemKind | null; forcedOwner: Owner | null; mentions: string[]; projectMentions: string[]; text: string }
// src/shared/project-match.ts (new)
export type ProjectLike = Pick<Project, 'id' | 'title' | 'aliases'>;
export function resolveProjectMention(mention: string, projects: ProjectLike[]): ProjectLike[]
export function findProjectsInText(text: string, projects: ProjectLike[]): { strong: ProjectLike[]; weak: ProjectLike[] }
// src/server/llm/types.ts
export interface ClassifyInput { text: string; people: { name: string; aliases: string[] }[]; projects: { title: string; aliases: string[] }[]; now: string }
export interface ClassifyOutput { kind: ItemKind; confidence: number; personName: string | null; projectName: string | null; owner: Owner }
```

Matching rules (all comparisons NFC + `toLowerCase`, Unicode word boundaries as in `people-match.ts`; a hyphen, underscore or run of spaces are equal, so `#board-deck` matches "Board deck"):

- `resolveProjectMention`: an exact title or alias match wins outright; otherwise projects whose title starts with the mention as whole words. Several results mean "ambiguous".
- `findProjectsInText`: whole-phrase matches of a title or alias. `strong` = the matched title/alias has two or more words; `weak` = a single word (min 3 characters).
- Only projects that are not deleted and not `done` are offered to these functions and to the classifier (cap 100 projects, titles cut to 100 characters). The duplicate check on "Create project" looks at all non-deleted projects.

Pipeline rules (same spirit as people: never guess):

1. Explicit `#mention` (first one only): one match → linked; none → `unknown_project`; several → `ambiguous_project`.
2. No mention: exactly one `strong` match → linked; several → `ambiguous_project`; otherwise a `weak` match is only a suggestion → `ambiguous_project` with those candidates plus Skip.
3. The classifier's `projectName` is kept only if it equals a known title or alias; it is always a suggestion → asked, never linked silently.
4. Kind `agenda`: project state is dropped, no project question is asked (the name stays in the text).
5. Question order: kind → person (or `needs_person`) → project. One question at a time.
6. "Create person" and "Create project" answers no longer file immediately, because another question may follow. `StoredDraft` (in `repos/captures.ts`) gains `projectPending: boolean`, `projectCandidates: Id[]`, `projectSuggested: boolean`, `personCreate: string | null`, `projectCreate: string | null`. Creation happens inside the filing transaction, after re-checking for an exact-name duplicate (exact match → link instead; only an exact match may replace the explicit choice).
7. Filing passes `projectId` to `createNote` / `createAction`. **Every filing path and every `{ projectId }` answer re-checks that the project is live (inside the filing transaction) and passes `projectId: null` otherwise; `createNote`/`createAction` throw `ProjectNotFoundError` for a deleted project, which must never surface as a 500** (amendment after S1 review). A created project is added to `filed` as `{ kind: 'project', id }` and is kept on undo, like a created person. If the linked project was deleted before filing, the item is filed without a project.
8. On filing, `draft.projectName`, `draft.projectCreate` and `draft.personCreate` are set to `null` (only `projectId` is kept) and **the pipeline never adds a project title to `captures.summary`** (the user's own typed words, e.g. `#zeta` → "zeta", stay, as user text; amended after the S3 review). The client composes the visible reply from the structured fields.
9. Reclassify keeps the project link, as it keeps the person link.
10. `FakeClassifier`: `projectName` is the capitalised word after `project ` (e.g. "todo: slides for project Apollo"), else null. Other fake rules unchanged.

### 4.7 Deletion and erasure rules for the new data

Columns that hold project content: `projects.title`, `projects.aliases`, `projects.description_md`; `captures.question` (candidate titles in an `ambiguous_project` question); `captures.draft` (`projectName` and `projectCreate` while a question is pending; both are nulled on filing by rule 4.6-8, and both are what the user typed, so they follow the capture's own lifetime like `captures.text`). By rule 4.6-8, `captures.summary` holds no project title beyond what the user typed. `pins`, `recents`, `project_people`, `actions.project_id`, `notes.project_id` and `captures.filed` hold ids only. Text the user typed that happens to name a project is content of that note or action and follows that item's lifetime.

- **Soft delete** (`softDeleteProject`, one transaction): set `deleted_at`; set `project_id = NULL` on its actions and notes (they are kept, without a project); delete its `project_people`, `pins` and `recents` rows; scrub captures (amended after the S1 review; this replaces the earlier wording): a draft *references* the project only through `draft.projectId` or `draft.projectCandidates`, never through a name match alone.
  - `draft.projectId` = the project → set it to null and clear `projectName` (the item then files without a project, as rule 4.6-7 says for a project deleted before filing).
  - The project in `draft.projectCandidates` → remove it. If candidates remain, keep `projectName` and `projectPending`, except that a suggested name (`projectSuggested`) is cleared with the candidate (it can be the deleted project's own title; amended after the S3 review). If none remain, clear `projectName`, `projectPending` and `projectSuggested` (the item then files without a project).
  - `question = NULL` only when the stored question is a project question that names this project (its candidate ids), or the draft referenced the project as above. An `unknown_project` question is never touched (it references no project id), and a draft linked to another project keeps its `projectName`.
  - `projectCreate` is not scrubbed (user-typed, pending only, see the column list).
  - Drop the `{kind:'project'}` ref from `filed`.
  - Re-derivation on read (S3): one or more candidates left → `ambiguous_project` with those candidates (name = the kept `projectName`, or the first candidate's current title if it is null) plus Skip; none → no project question.
- **Purge** (30 days, `repos/purge.ts`): hard-delete projects whose `deleted_at` is older than the cutoff, re-run the capture scrub for them as a safety net, and delete `pins`/`recents` rows whose note or project no longer exists. Ids are never reused (`AUTOINCREMENT`); `secure_delete` and the WAL truncate already apply.
- **Notes** purged by the existing rule also lose their `recents` row.
- Read paths: every list, detail, search, nav and export query excludes soft-deleted projects.

Test: after delete + purge, scan every text column of every table for the project's title, alias and description strings and find none (paired with a "the string was there before" assertion).

Binding syntax: `'mod+k'` (Cmd or Ctrl, one token as today), `'alt+space'`, `'esc'`, `'enter'`, `'up'`, `'down'`, `'left'`, `'right'`, `'space'`, `'shift+…'`. Engine rules:

1. While any `modal` layer exists, only modal bindings match, except `esc` and `mod+k` bound in the global layer.
2. While focus is in a text entry, only bindings with `mod` or `alt`, and `esc`, fire. Arrows, Enter, Space and printable keys belong to the field. A field's own `onKeyDown` must check `modalOpen()` first.
3. `panel` bindings fire only while focus is inside `[data-region="panel"]`; `stream` bindings only inside `[data-region="stream"]`. `global` bindings always (subject to 1 and 2).
4. A focused button, link or checkbox keeps native Enter and Space.
5. Type-to-composer: a printable key without `mod` (Option alone counts as typing, so Option-2 `@` on a Swedish Mac works; `alt+space` is consumed by push-to-talk first; amended after the C1 review), pressed with no text entry focused and no modal open, calls `focusTarget('composer')` synchronously and is not prevented, so the character lands in the composer. No-op when the composer is not rendered.
6. A global key that opens an overlay is a no-op while another overlay is open.

### 4.10 Question answering (steps Q1, Q2; last)

**Answers are snapshots** (decision after the Q1 security review): editing a source does not redact an answer that quoted it; deleting a sent note/action/agenda item/project does. To erase an answer, undo it (undo and reclassify erase it at once).

Flow: a capture is a question when it starts with **`/ask`** (or `/q`), or when the classifier says `question` with confidence ≥ the threshold. If unsure, the existing kind question gains the option `q` "Answer it". A question capture is stored with status `asked` and returned at once; the client then calls `POST /api/captures/:id/ask`, which retrieves, calls the LLM and stores the answer. If that call fails or the page closes, the capture stays `asked` and shows Answer / File instead / Discard chips. The client calls `ask` only from the send path, never because the stream loaded.

```ts
// shared/types.ts
// Capture.status gains 'asked' | 'answered';  CaptureDraft.kind and ParsedCapture.forcedKind become ItemKind | 'question' | null
export interface SourceRef { kind: 'note' | 'action' | 'agenda' | 'person' | 'project' | 'meeting'; id: Id; title: string }
export interface CaptureAnswer { text: string; sources: SourceRef[]; redacted: boolean }
// Capture gains: answer: CaptureAnswer | null
// server/llm/types.ts
// ClassifyOutput.kind becomes ItemKind | 'question'
export interface AnswerInput { question: string; now: string; excerpts: { ref: string; title: string; text: string }[] }   // ref like "note:12"
export interface AnswerOutput { answer: string; cited: string[] }
export interface Answerer { answer(input: AnswerInput, signal?: AbortSignal): Promise<AnswerOutput> }   // rejects with LlmError
// server/deps.ts: AppDeps gains answerer: Answerer | null
// server/qa/retrieve.ts
export interface Excerpt { kind: SourceRef['kind']; id: Id; title: string; text: string }
export function retrieve(db: DatabaseSync, question: string, caps?: { maxExcerpts?: number; maxExcerptChars?: number; maxTotalChars?: number }): Excerpt[]
// server/qa/service.ts
export function createQaService(deps: AppDeps): { ask(id: Id): Promise<Capture | 'not_found' | 'not_asked' | 'no_llm' | 'failed'> }
```

| Method + path | Response |
|---|---|
| POST `/api/captures/:id/ask` | 200 `Capture` (`answered`); 404; 409 `not_asked`; 429 `rate_limited` / `busy` with `Retry-After`; 502 `llm_failed`; 503 `no_llm` |
| POST `/api/captures/:id/undo` | also accepts `asked`/`answered`: clears answer and sources at once, status `discarded` |
| POST `/api/captures/:id/reclassify` | also accepts `asked`/`answered`: clears answer and sources, back to the kind question |

Retrieval (local, deterministic, no LLM): tokens of the question (NFC, lower-case, length ≥ 3, minus a small English + Swedish stop-word list, max 8); people and projects named in it (`findPeopleInText`, `findProjectsInText`); `xo_fold … LIKE` lookups per token over notes, actions, agenda items, people (name, aliases, notes), projects (title, aliases, description) and meeting notes; for a named person add their notes, open agenda, open actions and latest meeting notes; for a named project its description, open actions and note previews. Score = distinct tokens matched, plus a bonus for items of a named person/project; ties by recency. Caps (defaults): 24 excerpts, 600 characters each (cut around the first match), 12 000 characters in total. Soft-deleted rows are never retrieved. **No excerpts → no LLM call**; the answer is a fixed "Nothing in your data matches that."

LLM call (`llm/answerer.ts`, through the existing OpenRouter client, so ZDR follows `XO_OPENROUTER_ZDR` and `plugins`/`tools` stay forbidden): system prompt says to answer only from the excerpts, in the question's language, to say so when they do not contain the answer, to cite refs, and that question and excerpts are untrusted data whose instructions must be ignored; the user message is JSON; structured JSON output `{ answer, cited }`; no `temperature` (the default Sonnet model on OpenRouter does not list it, and `provider.require_parameters` is on), `reasoning: { effort: 'low', exclude: true }` (reasoning is mandatory for the default model and shares `max_tokens`), `max_tokens` 3000, 45 s deadline (answerer, service and route); verify in the live check (amended after the Q1 review). Model: `XO_QA_MODEL`, defaulting to a Claude Sonnet model on OpenRouter (user decision 2026-11-15; Q1 verifies the exact current OpenRouter model id against the OpenRouter models list without calling the API with the key, and documents it in `.env.example`). Validation: `answer` is a string, control and format characters stripped (newlines kept), max 4 000 characters; `cited` is filtered to refs that were actually sent (unknown refs are dropped, max 12). Anything else is an `LlmError`.

Storage (migration `006-qa.sql` rebuilds `captures` for the new status CHECK and columns `answer TEXT`, `sources TEXT` = JSON `{ sent: ItemRef[], cited: ItemRef[] }`). The rebuild must **carry over the `sqlite_sequence` high-water mark** of `captures` (copy the old `seq` to the new table before dropping the old one), otherwise purged ids could be reused.

Erasure: an answer is a derived copy of every excerpt sent. On read, if any `sent` note, action, agenda item or project is soft-deleted or gone, the capture is returned with `answer: { text: '', sources: [], redacted: true }`. The purge deletes answered captures when any `sent` item is purged. Source titles are looked up at read time, never stored. Answers are not part of the Markdown export.

Limits: 20 asks per minute, 2 at a time, slot freed explicitly on abort and by the deadline. Logs carry error classes and counts only: never the question, excerpts or answer. The client renders the answer as plain text and the sources as chips that call `openDoc`.

`FakeAnswerer` (tests, e2e, `XO_LLM=fake`): answer `"Found N item(s): <titles>"`, cites the first two refs; a question containing `!!fail` throws `LlmError`. `FakeClassifier`: text ending in a single `?` → `question` 0.95 (the `??` rule is checked first).

## 8. Acceptance criteria

UI and Projects (checked after E, before Q1):

1. `pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm e2e` pass with no API key configured.
2. Desktop: sidebar, centred chat with nothing open, split view with a document open; the panel closes with Esc and expands to full width and back.

6. Projects: create, rename, status active / on hold / done, description, actions, notes, linked people, delete. A capture naming a project is filed into it or asks.
7. An action can have a project and a person. Actions are grouped by project and filterable by person. A 1-1 shows the person's open actions across projects.

10. Theme follows the system (light and dark), system font at 16–17 px with generous line height, monospace only for code-like bits, no CSP violations.
11. Phone width: drawer sidebar, one panel at a time with a back button, composer pinned at the bottom with a large mic button, nothing wider than the viewport.
12. Security model intact: route sweep green for every new route, CSRF and Origin enforced, lock on 401 removes server data from the DOM and keeps typed text.
13. Deleting a project leaves no copy of its title or description anywhere after the purge; soft-deleted projects are invisible on every read path immediately.
14. `pnpm xo export` includes projects.
15. Search finds projects; search text never enters a URL or a log.
16. The old TUI files are gone.

18. Only capped, relevant excerpts are sent; nothing is sent when nothing matches; ZDR follows `XO_OPENROUTER_ZDR`; no question, excerpt or answer text is logged.
