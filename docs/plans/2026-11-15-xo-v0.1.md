# XO v0.1 — implementation plan

Date: 2026-11-15
Status: ready to implement (interview done by the coordinator; unsettled points are listed in section 12)

## 1. Objective

XO is a single-user, web-based "run my life" tool with a TUI look, fully controllable by keyboard and voice. v0.1 delivers the core loop: type or dictate something into a chat, have it classified and filed as a note, an action, or a 1-1 agenda item (linked to a person), and run 1-1 meetings from the accumulated agenda. It must be a small but solid base: one Node process, one SQLite file, real auth, clean seams for later features.

## 2. Scope

### In scope (v0.1)

- Login: password + TOTP, session cookie, CSRF protection, rate-limited login, single user bootstrapped via CLI.
- Document types: notes, actions, people, 1-1 meetings (agenda items + meeting notes + follow-up actions).
- Chat capture with hybrid classification: prefix commands force the type; otherwise an LLM (via OpenRouter, ZDR) classifies; when unsure it asks instead of guessing; one-key undo and reclassify.
- People linking: known names/aliases link automatically; unknown names ask before creating a person.
- Full 1-1 loop: agenda accumulates per person, start 1-1, check items off, unfinished items carry over, follow-up actions with owner (me/them), previous meeting visible.
- Voice: push-to-talk, server-side transcription via OpenRouter, dictation into the chat input plus a small set of voice commands.
- TUI: vim-style modal keys, command palette, box-drawing panes, monospace, dark theme with one accent colour. Mouse/touch works but is secondary.
- Search (simple substring search across all types).
- Markdown export CLI, Dockerfile, README with run/deploy notes.

### Out of scope (v0.1)

- Journal, projects, decisions, goals; calendar; cadence/reminders; due dates.
- Multi-user, password reset by email, passkeys, recovery codes.
- Markdown rendering (bodies are shown as plain monospace text — this is also a deliberate XSS-avoidance choice), attachments, tags.
- Multiple items from one capture, LLM chat/Q&A over the data, full-text index (FTS5), sync/offline, native mobile.
- Choosing/provisioning the hosting target, TLS termination (a reverse proxy does it), at-rest DB encryption.

## 3. Approach

- **One package, three source roots**: `src/shared` (types + pure logic used by both sides), `src/server` (Fastify + `node:sqlite`), `src/client` (Vite + Preact, hand-written TUI CSS).
- **No server build step.** Node 26 runs `.ts` directly via built-in type stripping. Consequences every programmer must follow:
  - Only erasable TypeScript syntax: no `enum`, no `namespace`, no constructor parameter properties (`erasableSyntaxOnly: true` enforces this).
  - All relative imports carry an explicit `.ts` / `.tsx` extension (also in `src/shared`, also in the client).
  - `import type` for type-only imports (`verbatimModuleSyntax: true`).
- **Dependency injection through one factory**: `buildApp(deps)` takes the DB handle, classifier, transcriber, clock and config. Tests pass an in-memory DB and fakes. Route modules are Fastify plugins that receive `deps` and know nothing about auth; a single global guard protects everything under `/api` (fail closed).
- **Contracts first.** Step 1 fixes the shared types, DB schema, API shapes, interfaces and creates stub files at the final paths, so the parallel steps only fill in files they own.
- **Classification is a small state machine on the server** (the "capture pipeline"): parse prefix → resolve person → decide kind (forced or LLM) → ask the user for whatever is unresolved → file. Person matching for known names is deterministic code, not the LLM. Any LLM failure, invalid output or low confidence turns into a question to the user — never a guess.
- **Minimal dependencies** (all installed in step 1, so no later step edits `package.json`):
  - runtime: `fastify`, `@fastify/cookie`, `@fastify/static`, `@fastify/helmet`, `qrcode` (terminal QR in the setup CLI only), `preact`, `@preact/signals`
  - dev: `typescript`, `vite`, `@preact/preset-vite`, `vitest`, `@playwright/test`, `@types/node`, `@types/qrcode`
  - Password hashing (scrypt), TOTP (HMAC-SHA1, RFC 6238), session tokens, and rate limiting use `node:crypto` / plain code — small, and tested against RFC vectors. The OpenRouter calls use global `fetch`.

Verified during planning: Node v26.12.0 and pnpm 12.15.0 are installed; `node:sqlite` works without flags (SQLite 3.54.1, FTS5 present); the project is already a git repository (branch `main`, remote `origin`) containing only the coordinator's committed `CLAUDE.md` and `.gitignore`, plus the untracked, git-ignored `.openrouter-key`. OpenRouter docs (fetched 2026-11-15): `POST https://openrouter.ai/api/v1/audio/transcriptions` accepts a JSON body `{ model, input_audio: { data: <base64>, format }, language?, provider? }` and returns `{ text, usage }`; `provider` accepts `zdr` and `data_collection`, while `order/only/ignore` are not applied to transcription; the multipart variant does not list `provider` among its supported fields, so **use the JSON body**. Per-request ZDR is `provider: { zdr: true }`.

### 4.3 Database schema (`src/server/db/migrations/001-init.sql`)

All timestamps are ISO-8601 UTC strings. `migrate.ts` applies numbered files in order using `PRAGMA user_version`. `open.ts` sets `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`.

```sql
CREATE TABLE user (
  id INTEGER PRIMARY KEY CHECK (id = 1),
  password_hash TEXT NOT NULL,          -- scrypt$N$r$p$saltB64$hashB64
  totp_secret TEXT NOT NULL,            -- base32
  totp_last_step INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
CREATE TABLE sessions (
  token_hash TEXT PRIMARY KEY,          -- hex sha256 of the cookie token
  csrf_token TEXT NOT NULL,
  created_at TEXT NOT NULL, last_seen_at TEXT NOT NULL, expires_at TEXT NOT NULL
);
CREATE TABLE people (
  id INTEGER PRIMARY KEY, name TEXT NOT NULL, aliases TEXT NOT NULL DEFAULT '[]',  -- JSON string[]
  notes_md TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL, archived_at TEXT
);
CREATE TABLE meetings (
  id INTEGER PRIMARY KEY, person_id INTEGER NOT NULL REFERENCES people(id),
  started_at TEXT NOT NULL, ended_at TEXT, notes_md TEXT NOT NULL DEFAULT ''
);
CREATE UNIQUE INDEX meetings_one_active ON meetings(person_id) WHERE ended_at IS NULL;
CREATE TABLE notes (
  id INTEGER PRIMARY KEY, title TEXT NOT NULL, body_md TEXT NOT NULL DEFAULT '',
  person_id INTEGER REFERENCES people(id),
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL, deleted_at TEXT
);
CREATE TABLE actions (
  id INTEGER PRIMARY KEY, text TEXT NOT NULL,
  owner TEXT NOT NULL CHECK (owner IN ('me','them')),
  status TEXT NOT NULL DEFAULT 'open' CHECK (status IN ('open','done')),
  person_id INTEGER REFERENCES people(id), meeting_id INTEGER REFERENCES meetings(id),
  created_at TEXT NOT NULL, done_at TEXT, deleted_at TEXT
);
CREATE TABLE agenda_items (
  id INTEGER PRIMARY KEY, person_id INTEGER NOT NULL REFERENCES people(id), text TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'open' CHECK (status IN ('open','done','dropped')),
  created_at TEXT NOT NULL, resolved_at TEXT, resolved_meeting_id INTEGER REFERENCES meetings(id),
  deleted_at TEXT
);
CREATE TABLE captures (
  id INTEGER PRIMARY KEY, text TEXT NOT NULL,
  source TEXT NOT NULL CHECK (source IN ('text','voice')),
  status TEXT NOT NULL CHECK (status IN ('pending','filed','undone','discarded')),
  draft TEXT NOT NULL,                  -- JSON CaptureDraft
  question TEXT,                        -- JSON CaptureQuestion or NULL
  filed TEXT NOT NULL DEFAULT '[]',     -- JSON ItemRef[]
  summary TEXT NOT NULL DEFAULT '',
  classified_by TEXT CHECK (classified_by IN ('prefix','llm','user')),
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
CREATE INDEX actions_open ON actions(status, deleted_at);
CREATE INDEX agenda_person ON agenda_items(person_id, status);
CREATE INDEX notes_person ON notes(person_id);
```

Carry-over needs no extra table: a person's agenda is their `open` agenda items. Checking an item during a meeting sets `status='done'`, `resolved_at`, `resolved_meeting_id`. Whatever is still open after "end meeting" is simply the agenda for the next one.

### 4.7 Shared pure logic (step 6)

```ts
// src/shared/capture-syntax.ts
export interface ParsedCapture { forcedKind: ItemKind | null; forcedOwner: Owner | null; mentions: string[]; text: string }
export function parseCapture(raw: string): ParsedCapture
// src/shared/people-match.ts
type PersonLike = Pick<Person, 'id' | 'name' | 'aliases'>
export function resolveMention(mention: string, people: PersonLike[]): PersonLike[]      // candidates for an explicit @mention
export function findPeopleInText(text: string, people: PersonLike[]): PersonLike[]       // distinct known people named in free text
// src/shared/voice-commands.ts
export function parseVoiceCommand(transcript: string, people: PersonLike[]): VoiceCommand | null
```

Prefix grammar: a leading `/note` (`/n`), `/todo` (`/t`, `/action`) → action owned by me, `/wait` (`/w`) → action owned by them, `/agenda` (`/a`) → agenda item. `@name` or `@"Full Name"` anywhere marks an explicit person mention; in the returned `text` the prefix command is removed and `@name` is replaced by the plain name. Unknown `/xyz` is not a command (text stays as is, `forcedKind` null).

Matching rules: case-insensitive, Unicode-aware (names like "Åsa", "Björn" must work — use `\p{L}`-based boundaries, not `\b`), whole-word only. `resolveMention` matches the full name, any alias, or the first word of the name. `findPeopleInText` matches full names and aliases, plus first names only when that first name is unique among the given people.

### 4.8 Capture pipeline (step 7, `src/server/capture/service.ts`)

```ts
export function createCaptureService(deps: AppDeps): {
  submit(text: string, source: 'text' | 'voice'): Promise<Capture>
  answer(id: Id, answer: { key: string } | { personId: Id }): Promise<Capture | 'not_found' | 'not_pending' | 'bad_answer'>
  undo(id: Id): Capture | 'not_found' | 'not_filed'
  reclassify(id: Id): Capture | 'not_found' | 'not_filed'
  list(opts: { limit: number; before?: Id }): Capture[]
}
```

Rules:

1. `parseCapture(raw)`. Empty text after parsing → 400.
2. Person: explicit mentions first (`resolveMention`: exactly one → linked; none → `unknown_person`; several → `ambiguous_person`). Only the first mention is used in v0.1. Without a mention, `findPeopleInText`: exactly one → linked; several → `ambiguous_person` (with skip); none → nothing yet.
3. Kind: `forcedKind` if present (`classifiedBy='prefix'`, no LLM call). Otherwise call the classifier with a 15 s timeout. If `deps.classifier` is null, it throws, or `confidence < threshold` → `kind` question. If confident → `classifiedBy='llm'`; `owner` from the output; if it names a person and none is linked yet, run `resolveMention` on that name (one → link, none → `unknown_person`, several → `ambiguous_person`).
4. Questions are asked one at a time in the order kind → person. `needs_person` is asked when kind is `agenda` and no person is linked or pending. When the user answers the `kind` question, `classifiedBy='user'`.
5. Filing (single DB transaction with the capture update): note → `createNote({ bodyMd: text, personId })`; action → `createAction({ text, owner, personId })`; agenda → `createAgendaItem`. "Create person" answers create the person first and add it to `filed`. `summary` is a one-line human-readable result.
6. `undo` soft-deletes the filed note/action/agenda item (a person created by the capture is kept). `reclassify` does the same, then sets the capture back to `pending` with a `kind` question and `draft.kind=null` (person link is kept).
7. The capture text is untrusted data for the LLM: the classifier output is used only after strict validation (enum kind, numeric confidence, string-or-null name); nothing from the LLM is ever executed or used as an id.

### 4.9 Auth design (step 2)

- **Bootstrap**: `pnpm xo setup` (interactive CLI). Prompts for a password twice without echo (min 12 chars), generates a 160-bit TOTP secret, prints the `otpauth://totp/XO:xo?secret=…&issuer=XO` URI, the base32 secret and a terminal QR code, then requires one valid TOTP code before writing the `user` row. Re-running requires `--force`, which replaces the credentials and deletes all sessions. There is no web sign-up; with no user row every login fails with the generic 401 and the server logs a one-line hint at startup.
- **Password**: `crypto.scrypt`, N=2^17, r=8, p=1, 16-byte salt, 64-byte key, parameters encoded in the stored string, `timingSafeEqual` compare.
- **TOTP**: RFC 6238, SHA-1, 6 digits, 30 s step, window ±1 step, replay protection (reject a step ≤ `totp_last_step`, update on success), constant-time compare.
- **Login**: one request with password + TOTP; a single generic error for any failure; password hash is always computed (no early exit).
- **Rate limit** (in-memory): 5 failed logins per IP per 15 min and 20 failed logins globally per 15 min → 429 with `Retry-After`. Counted before verification so a locked-out caller costs no scrypt work.
- **Session**: 32 random bytes (base64url) in cookie `__Host-xo_session` — `HttpOnly; Secure; SameSite=Strict; Path=/`; only the SHA-256 hash is stored. Absolute and idle expiry per config; expired rows purged at startup and on login. With `XO_COOKIE_INSECURE=true` (dev) the cookie is `xo_session` without `Secure`.
- **Guard** (`auth/guard.ts`, global `onRequest` hook): every `/api/*` route except `GET /api/health` and `POST /api/auth/login` requires a valid session. Every non-GET/HEAD request (login included) must carry an `Origin` header equal to `XO_PUBLIC_ORIGIN`; authenticated non-GET requests must also carry `X-XO-CSRF` equal to the session's CSRF token (constant-time compare). Login additionally requires `Content-Type: application/json`.
- **Headers**: `@fastify/helmet` with a strict CSP (`default-src 'self'`; no inline scripts; `connect-src 'self'`; `media-src 'self' blob:`; `frame-ancestors 'none'`), `Referrer-Policy: no-referrer`, `Permissions-Policy: microphone=(self)`.
- **Logging**: Fastify logger with request bodies never logged; redact `authorization` and `cookie` headers; never log capture text, transcripts, passwords, TOTP codes or the API key.

### 4.10 Client design (steps 5, 8, 9, 10)

Box-drawing borders, one monospace font stack, dark neutral palette with a single accent colour, all colours as CSS custom properties in `tui.css`. Works down to phone width (nav collapses); touch targets are the same list rows and buttons.
- Modes: NORMAL (keys are commands), INSERT (focus is in an input/textarea; `Esc` returns to NORMAL), COMMAND (palette open).

### Amendments from the step 1 review (2026-11-15, binding for all later steps)

These override anything above that conflicts with them.

- **Guard model (step 2):** auth is decided by the *matched route*, never by the raw URL (the router percent-decodes paths, so `/%61pi/...` matched `/api/...` while a raw `startsWith('/api/')` check missed it). All `/api` routes live in one `/api`-prefixed scope whose `onRequest` hook is the guard. Public routes opt out with `config: { public: true }`: `GET`/`HEAD /api/health` and (step 2) `POST /api/auth/login`. Unmatched requests fall back to a decoded-path check that answers 401 for `/api*`. Expired sessions are purged inside `authGuard()` at startup (it runs once from `buildApp`) and on login.
- **Validation:** ajv runs with `coerceTypes: false` and `removeAdditional: false`. Querystring and params values are strings (digit `pattern`) converted in handlers; nullable body fields declare `['integer','null']` etc.
- **Search** is `POST /api/search` with a JSON body. The client route `#/search` keeps the query in client state, not in the URL.
- **Client root** is `src/client` (`index.html` lives there). Vite binds to 127.0.0.1 only with a strict `server.fs.deny`; never run Vite with `--host`.
- **API key** is not part of the shared `Config` that route modules see; only the OpenRouter factory receives it (step 4). CLI commands never load it.
- **Errors:** only `HttpError`, Fastify validation errors and `FST_ERR_*` codes relay a 4xx message. Step 4 must wrap every upstream failure in `LlmError` and never attach upstream bodies or user text to errors.
- **Trust proxy:** `XO_TRUST_PROXY` is `false`, a hop count, or an IP/CIDR list; `true` is rejected. Step 2's rate limiter keys on `req.ip`, which is trustworthy only with that setting.
- **Step 2 extras:** small `bodyLimit` on login; compare `Origin` only against `config.publicOrigin` (never `Host`/`X-Forwarded-Host`); log login failures and lockouts with `req.ip` and never credentials.
- **Step 4 extras:** hard-coded OpenRouter base URL (not env-configurable); `fetch` with `redirect: 'error'`; the raw-audio content-type parser is scoped to the voice route only.
- **Step 11 extras:** the Dockerfile uses `pnpm install --frozen-lockfile` and sets `NODE_ENV=production`; README/Caddy publish the Node port to the proxy only (`127.0.0.1:3000` or an internal Docker network) and set `XO_TRUST_PROXY` accordingly; Caddy access logs don't record request bodies; export creates its directory 0700 and files 0600; `HEALTHCHECK` uses GET (HEAD also works).

- **Locked public route set (steps 2 and 12):** a test asserts the routes with `config.public` are exactly `GET`/`HEAD /api/health` and `POST /api/auth/login`.

## 8. Acceptance criteria (v0.1 is done when all hold)

1. `pnpm install && pnpm typecheck && pnpm test && pnpm build && pnpm e2e` pass on a clean checkout with no API key configured.
2. `pnpm xo setup` creates the single user; logging in requires the correct password and a current TOTP code; a reused code, a wrong password and a wrong code are all rejected with the same message; repeated failures are rate-limited.
3. Without a session, every `/api` route except health and login returns 401; state-changing requests without the CSRF header or with a foreign Origin return 403. The session cookie is HttpOnly, Secure, SameSite=Strict (in non-dev mode).
4. Typing `/note …`, `/todo …`, `/wait …`, `/agenda @person …` files the right item without an LLM call and shows the result line.
5. An unprefixed capture is classified by the LLM; a confident result is filed with a visible result; `u` undoes it and `r` reopens the classification choice.
6. When the LLM is unsure, fails, or no API key is set, nothing is filed until the user picks a kind from the inline, keyboard-selectable question.
7. A capture naming a known person (name or alias, including non-ASCII names) is linked automatically; an unknown `@name` or LLM-detected name asks before creating a person; an ambiguous name asks which person.
8. 1-1 loop: agenda items added over time appear when starting a 1-1; items can be checked off; follow-up actions can be added for me and for them; notes are saved; after ending, unchecked items appear in the next 1-1, and the previous meeting's notes, resolved items and follow-ups are visible there.
9. Every function is reachable by keyboard: view switching (`g`-prefixes), list movement, search (`/`), command palette (`:` / `Ctrl-K`), help (`?`); the same works by mouse/touch.
10. Holding the push-to-talk key records, releasing transcribes; "open Anna", "start 1-1 with Anna" and "go to actions" execute; any other transcript lands in the chat input for confirmation with Enter.
11. When `XO_OPENROUTER_ZDR=true`, every request to OpenRouter (chat and transcription) carries a forced `provider: { zdr: true }` with no retry without it; when false (the default for now), no `zdr` is sent; the API key comes only from `OPENROUTER_API_KEY` or the git- and docker-ignored key file, and appears in no log line, error message, client bundle, Docker image or committed file.
12. All data lives in one SQLite file outside the repo (`XO_DB_PATH`); `pnpm xo export` writes a readable Markdown tree of people, meetings, notes and actions.
13. `docker build` succeeds and the container serves the app with the DB on the `/data` volume, running as a non-root user.
14. The UI is monospace with box-drawing panes, a dark neutral theme and one accent colour, and is usable at phone width.

## 11. Risks and mitigations

| Risk | Mitigation |
|---|---|

| TOTP secret and all content are plaintext in the SQLite file | File mode 0600, directory 0700, DB outside the repo; at-rest encryption deferred (later versions). |
| In-memory rate limiter resets on restart and is per-process | Acceptable for one process; revisit if the deployment model changes. |
| Prompt injection through captured text | LLM output is only an enum/number/name after strict validation; worst case is a misfiled item, which undo/reclassify fixes. |
| Browser key conflicts (`Space` scrolling, `Alt+Space`, `Ctrl-K` in some browsers, Safari `MediaRecorder` mime types) | `preventDefault` on handled keys; bindings centralised in `lib/keys.ts` so they are easy to change; mime fallback; manual Safari check. |
| Contract drift between parallel steps | Contracts are code from step 1; changes only via the coordinator; step 12 integration test and smoke test catch mismatches. |
| LLM cost/latency per capture | Small fast default model, `max_tokens` cap, 15 s timeout, prefixes bypass the LLM entirely. |

## 12. Assumptions / open questions

Assumptions made because the interview did not settle them (each is easy to change before or during implementation):

1. **Bootstrap** via interactive CLI `pnpm xo setup` (not env vars), with TOTP confirmation and `--force` to reset. No recovery codes.
2. **Password hashing** with scrypt from `node:crypto`, and **TOTP hand-implemented** on `node:crypto` (tested against RFC 6238 vectors) rather than adding libraries. If the security reviewer prefers a vetted library (e.g. `otpauth`) or Argon2id, swap inside `auth/password.ts` / `auth/totp.ts` only.
3. **Agenda item is its own capture kind** (`note | action | agenda`), and "attach to a person" means a person link on a note or action.
4. **One capture → one item.** Splitting a multi-part thought into several items is deferred.
5. **Prefix set**: `/note`, `/todo`, `/wait` (action owned by them), `/agenda`, `@person`. With a forced prefix no LLM call is made, so unknown people are only detected when written as `@name`.
6. **Confidence threshold** 0.8 (configurable); model defaults `anthropic/claude-haiku-4.5` (classifier) and `openai/whisper-1` (transcription) — both to be verified against OpenRouter at implementation time.
7. **Push-to-talk keys**: hold `Space` in NORMAL mode, `Alt+Space` in any mode, plus a mic button. Dictated text is placed in the chat input and needs `Enter` (no auto-submit); voice commands execute immediately.
8. **Integer ids** and **soft delete** for notes, actions and agenda items; people are archived, not deleted; meetings cannot be deleted in v0.1.
9. **Markdown is stored but shown as plain text** (no renderer) in v0.1.
10. **Search** is substring (`LIKE`) search; FTS5 is available in the bundled SQLite for later.
11. **Session lifetime** 30 days absolute, 7 days idle; login lockout 5 failures / 15 min per IP, 20 globally.
12. **Undo** keeps a person that the undone capture created.
13. **No linter/formatter** in v0.1 beyond `tsc --strict`; add later if wanted.
14. **Production runs TypeScript directly** with Node 26 type stripping (no compiled server output).
